# Grant one Karma point and one Humor point per Message, and spend them once

ADR-0002 let Karma plus and Karma minus be active on the same Message at once, cancelling only in the net total, and ADR-0004 made every reaction-sourced Mark reversible forever. Together they made a Mark cheap: an Actor could hold both Karma Marks on one Message, and could withdraw and re-place any of them indefinitely. Scoring meant less than the Chat believed it did.

Marking is now spending a grant. For every other Member's Message an Actor holds one Karma point, spendable as plus or minus but never both, and one Humor point, independent of it. Spending is permanent and the input does not matter: a `-` Scoring reply after a 👍 Scoring reaction is refused exactly as a second 👍 is, and neither is announced. The one concession is the Undo window — removing a Scoring reaction within five seconds of adding it takes the Mark back and refunds the grant. After that the Mark stands and removing the reaction does nothing.

The Undo window is a comparison of two Telegram timestamps, not a delayed write. The removal and the addition both carry Telegram's own `date`, and the addition's is already stored on the Mark, so no timer, queue, or deferred commit is involved; the check is deterministic under webhook retries and testable without waiting. As in ADR-0003, Telegram's timestamps decide, never bot processing time. A Mark's `source` guards the window too, since only `reaction` Marks can be taken back — without it, removing a 👎 that was itself refused would delete the `-` reply already occupying the Karma slot.

This replaces ADR-0004 entirely. The append-only log of additions and same-type reversal Events existed to support unlimited reversibility; with Marks permanent, the only mutation left is a five-second undo of something accidental, whose history is worth nothing. So `events` becomes `marks`, one row per spent grant, with `(chat_id, actor_id, message_id, slot)` as its primary key and `slot` generated from `type` so the two cannot drift. Uniqueness is now a database constraint rather than application code holding a Message-row lock, which retires that lock, the active-Mark subquery, the reversal columns and their constraints, and the sign inversion in aggregation. Adding is one `INSERT ... ON CONFLICT DO NOTHING`; undoing is one `DELETE` bounded by the window. Neither reads first, and the vocabulary loses "Event" and "Active Mark" — every row is simply a Mark.

Imported v1 Marks obey the same rule and are otherwise ordinary Marks. v1 had no reactions — every v1 row was a `+`, `-`, or `лол` reply — so an Imported Mark is stored as a Scoring reply Mark, which already carries the permanence it needs. There is no `import` source: `legacyId` alone tells an Imported Mark from a native one, and only Season attribution reads it. v1 also permitted repeat marking, so 57 of 32,389 rows would spend a grant twice; the import keeps the earliest per grant and drops the rest, shifting a few historical Season totals by one or two points. Byte-exact v1 history was the alternative, but it would have meant a partial index and two different rules for the same table, and the Leaderboards it protects are already best-effort about Message dates (ADR-0003).

`processed_updates` keeps earning its place under this model: without it, a redelivered addition arriving after an undo would resurrect a Mark the Actor had just taken back.
