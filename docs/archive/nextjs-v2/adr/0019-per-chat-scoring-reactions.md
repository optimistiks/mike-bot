# Let each Chat choose its Scoring reactions, one Mark per reaction

ADR-0002 named three reactions — 👍, 👎, 🤣 — and every Chat has scored by exactly those since. The names were a global constant, so a group that expresses approval with a 🤡 or laughs with a 😁 had no way to say so, and custom emoji could not place a Mark at all: the reaction reader recognised three literal strings and threw away everything else, custom emoji included, even though it had always known how to name them.

A Chat's administrators now choose. `chat_scoring_reactions` holds one row per reaction a Chat has put in play, and that row carries the single Mark type the reaction places. The primary key `(chat_id, reaction_key)` is the whole of the enforcement: a reaction has exactly one `mark_type` column, so binding one reaction to two Marks is not a state the table can hold. Nothing is checked because nothing can be wrong — the same move ADR-0015 made, where a second Mark in a slot loses to the key rather than being read for first. Rebinding 🤣 from Humor to Karma plus is one upsert that takes it away from Humor as a consequence of the write, with no window in which it is both and no application code trusted to notice.

Absence of rows is what says "never configured". A Chat with no rows scores by the built-in bindings, which is why this shipped without backfilling a single existing Chat, and why the defaults live in code rather than in every Chat's rows. That rule only stays total because rows are inserted and re-typed, **never deleted**. A Chat may deliberately bind nothing to Karma minus, or to anything at all; if unbinding removed rows, a Chat that emptied its whole mapping would read as unconfigured and silently start scoring by 👍👎🤣 again. So a save first unbinds everything, then materialises a row for each built-in reaction, then writes what was asked. `mark_type` NULL means the reaction is in the Chat's palette and scores nothing — one column doing the work a second table would otherwise do.

`/addreaction <emoji>` exists because a Mini App cannot offer a custom-emoji picker. Telegram's custom-emoji keyboard is native client UI, and the Bot API can render an id it is given but cannot enumerate what exists, so the id has to arrive from a person's own client. Taking it as an argument to the command — rather than collecting a reaction on a bot-posted message, which was the first design — is what keeps `readUpdate` a total function of the update: a standard emoji is text, a custom one is a `custom_emoji` entity carrying its id, and both are in the message already. No capture row, no expiry, no sweep, and no Telegram call anywhere in the webhook path. Telegram also writes a stand-in emoji into the text beneath a custom-emoji entity, so the label the Mini App draws comes free from the same message instead of from `getCustomEmojiStickers`.

The command is deliberately open to any Member. It adds an _unassigned_ reaction to a palette and cannot change what anyone scores; only binding does that, and binding is administrators-only in the Mini App. Gating the command would have bought a permission on a suggestion, and cost the property that makes the design work: admin status is not in the update, so the check would mean either a Telegram call inside the update transaction — the unbounded-await hazard that `.scratch/chat-metadata-refresh/issues/01` was open about — or an admin snapshot hoisted into the pure reader. The command is also the _only_ way a palette grows: saving in the Mini App binds reactions the Chat already holds and refuses a key it has never seen, so nothing can reach a binding without passing the checks below. Nothing bounds how large a palette may get. A Member could pad one with `/addreaction`, but the palette is admin-facing, the additions score nothing, and a cap would be machinery carried against a group griefing itself — worth adding the day that happens, and not before.

A reaction is also refused unless Telegram allows it. `/addreaction 🍕` would otherwise reach the palette, an administrator would bind it, and the Mark would never fire, with nothing anywhere saying why — a failure with no surface, like the reaction/Mark divergence ADR-0015 closes on. The allowed set is typed as grammY's own union so the compiler checks it against the Bot API rather than trusting a transcription, and reaction emoji are normalised against the variation selector, since a person types ❤️ and Telegram names that same reaction ❤.

Changing what a Chat scores by is a new permission, and it extends ADR-0009 rather than contradicting it. Registration remains authorization to _view_ a Chat: any registered Member may read the bindings, which is worth reading even when they cannot be changed. Administration is a further gate on _changing_ them, asked of Telegram with `getChatMember` each time the settings screen is opened or saved. Nothing caches it: the question is asked twice per visit to a screen most Chats will open rarely, it is the security boundary, and a cache would answer it from stale data — a Member demoted a minute ago would still be able to save. The call is bounded by a timeout, the same fix applied to the older `getChat` in passing, and a Chat Telegram will not answer for is treated as administered by nobody, since refusing the save is the safe direction.

Three things are accepted rather than solved. Rebinding is retroactively lossy for the Undo window: removals are mapped through the _current_ bindings, so unbinding a reaction while an Actor's five seconds are still open means removing it no longer refunds the slot. Versioning bindings per Mark would fix it and is not worth it for a five-second race. Second, Telegram lets a Chat narrow which reactions its members may use, and Mike-bot does not read that list, so an administrator can bind a reaction their own Chat forbids; the allowed-set check catches the global case but not the per-Chat one. Third, sending a custom emoji requires Telegram Premium of the sender, and reacting with one requires it of every reactor, so a Chat can bind a reaction most of its Members cannot place — visible in the Mini App, invisible in the Chat.
