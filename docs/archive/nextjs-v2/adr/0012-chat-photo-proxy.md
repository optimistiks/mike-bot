# Mirror Chat titles and photo references, stream photo bytes through an authenticated proxy

The Mini App needs each Chat's name and avatar, but Telegram remains their owner: Postgres stores the latest title, the small-photo file reference, and a stable photo version, never image bytes. `/api/chats/[chatId]/photo` authenticates the Member, requires their Registration in that Chat, resolves the current Telegram file path, and streams the bytes, so `BOT_TOKEN` never reaches a client and a Chat's photo stays exactly as private as the Chat. The client holds the resulting Blob in its in-memory query cache only and falls back to title initials.

The alternative — copying images into our own object storage — would buy a friend-group project little beyond a blob store to maintain and a second copy of data Telegram already keeps current. The cost accepted instead is an extra authenticated request per Chat, a stale file reference refreshed on demand, and no photo at all when the bot cannot reach Telegram.

Member profile photos follow the same proxy but store nothing at all. `/api/members/[userId]/photo` authenticates the caller, requires that the two share a Chat — the caller holds a Registration in a Chat the subject has a Display identity in — and streams the smallest size Telegram offers. Nothing about a profile photo is mirrored because nothing versions it: Telegram exposes no identifier the app could cache against, so the browser's hour-long cache is what decides when a changed photo appears, and the standings fall back to initials for every failure alike — no photo, a private profile, or Telegram unreachable. Keying the endpoint by Member rather than by Chat is deliberate: one face is fetched once for every Leaderboard it appears on.

Photo bytes are cached with `'use cache: remote'` (ADR-0013), keyed so that the volatile question and the expensive one are asked at different rates. `file_id` names an immutable file — a changed photo is a new id, never new bytes under the old one — so the download is remembered for a day and invalidates itself. Which file is a Member's avatar *right now* has no such identifier, so that one-call lookup is remembered for an hour, and it alone decides how quickly a changed profile photo appears. A failed lookup is cached for a minute: not caching it re-asks Telegram about every photoless Member on every render, and caching it as long as a success would pin one flaky request in place for days. Authorization is never cached — it is per Member, the bytes are not, and a cached permission answer is how someone who left a Chat keeps seeing its photo.

The remote handler is what makes this worth anything: a serverless instance is discarded between requests, and an in-memory entry with it. The failure mode to watch is silent — with no platform handler, `remote` falls back to the in-memory one and behaves exactly like `use cache`, correct but nearly always missing — so the check after deploy is Telegram call volume, not an error log.
